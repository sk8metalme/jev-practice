# 14の横断的傾向

出典: https://sk8metalme.github.io/thinking/oss/oss-design-philosophy.html （件数は100プロジェクト中の該当数）

どの傾向も「トレードオフの宣言」である。何かを取るなら何かを捨てる。その捨てたものを書くのが哲学。

各傾向の最後の「リポジトリで確認する観点」は、このSkillがReviewモードで使う判定基準。

## 1. 段階的採用と相互運用（32件）

既存の標準・ツール・競合とつながり、少しずつ導入できるようにする。

- 効く理由: 乗り換えコストが低く、採用のハードルが下がる。
- 落とし穴: 互換対応の範囲が広がりすぎると保守が重くなる。
- 取り入れ方: 入出力を標準形式に合わせ、既存ツールとの併用手順を書く。
- 例: TypeScript、Vue、Astro、Biome、Grafana、OpenTelemetry
- リポジトリで確認する観点: 入出力が標準形式（JSON、JSONL、標準の設定ファイル）か。既存ツールと一緒に使う手順があるか。部分導入（opt-in、shadow、dry-run）ができるか。**導入したら戻せるか（uninstall / rollback）。**

## 2. 哲学を明文化する（29件）

設計原則・マニフェスト・Doctrineなどを文書で公開し、判断の根拠を共有する。

- 効く理由: 要望や議論への答えが個人の好みではなく方針になる。新しい貢献者が判断基準を学べる。
- 落とし穴: 抽象的すぎると使えない。具体例とトレードオフを添える。
- 取り入れ方: 「解く問題」「原則」「やらないこと」の3節から始める。
- 例: Rust、TypeScript、Zig、htmx、Astro、Ruby on Rails
- リポジトリで確認する観点: PHILOSOPHY.md、または同じ役割の節があるか。原則が1か所にまとまっているか（READMEやissueに散らばっていないか）。エージェント向けの指示（AGENTS.md）から参照されているか。

## 3. 開発者の幸福を中心に置く（28件）

使っていて楽しい・気持ちいい体験を明確な目標にする。

- 効く理由: 感情的な愛着が生まれ、口コミで広がる。
- 落とし穴: 主観的になりやすいので、具体的な体験（待ち時間、エラー文）に落とす。
- 取り入れ方: 最初の5分の体験（インストールから最初の成功まで）を磨く。
- 例: Vue、Ruby on Rails、PyTorch、Ruby、Kotlin、Elixir
- リポジトリで確認する観点: READMEの最初の画面で「インストール → 最初の成功」まで行けるか。READMEの行数（長すぎる入口は減点）。エラー文に次の一手が書いてあるか。診断コマンド（doctor）が次のステップを示すか。インストールした環境で既定値のまま動くか（リポジトリ相対パスに依存していないか）。

## 4. 持続性・統治・ライセンス（26件）

財団、非営利化、資金モデル、ライセンス選択などで長期存続を設計する。

- 効く理由: 「突然消える・変わる」不安を減らし、企業も採用しやすくなる。
- 落とし穴: ライセンスの一方的な変更はフォークと信頼低下を招く。
- 取り入れ方: 作者が関われなくなった場合にどうするかを一度考えて書いておく。
- 例: Rust、Zig、Vue、Django、Biome、Ghostty
- リポジトリで確認する観点: LICENSEファイルがあり、パッケージの宣言（Cargo.toml、package.json など）と一致しているか。メンテナンス終了時の方針が書いてあるか。

## 5. 個人の痒みから始まる（25件）

作者自身の具体的な不満や必要が出発点になっている。

- 効く理由: 要件が現実的で、作者が最大のユーザーとして品質を保てる。
- 落とし穴: 自分以外の用途を見落としやすい。
- 取り入れ方: READMEの冒頭に「なぜ作ったか」を自分の言葉で書く。
- 例: Vue、Ruby on Rails、Django、Ghostty、curl、Linux
- リポジトリで確認する観点: README冒頭に動機があるか。機能一覧から始まっていないか。

## 6. 単純さと明示性を優先する（24件）

暗黙の便利さより、理解しやすく予測可能な振る舞いを選ぶ。

- 効く理由: デバッグしやすく、長期の保守コストが下がる。
- 落とし穴: 初心者にとっての「手軽さ」を失いすぎないようにする。
- 取り入れ方: 「魔法」を入れるときは、それなしでは得られない大きな利便性があるか確認する。
- 例: Go、Zig、htmx、Django、PyTorch、scikit-learn
- リポジトリで確認する観点: 黙って切り詰めたり、フォールバックしたり、自動で書き換えたりしていないか。副作用のあるコマンドにdry-runがあるか。失敗が明示的な状態として返るか。

## 7. 速さをアイデンティティにする（22件）

性能を最優先の価値として掲げ、他の判断基準にする。

- 効く理由: 違いが数字で伝わり、機能要望を断る基準も明確になる。
- 落とし穴: 速さだけでは乗り換えない。互換性や導入しやすさと組み合わせる。
- 取り入れ方: ベンチマークの方法と結果を公開し、性能劣化をCIで検出する。
- 例: Astro、esbuild、Biome、Ghostty、Bun、Svelte
- リポジトリで確認する観点: 性能を主張しているなら、計測方法と再現条件が公開されているか。CIがあるか（テスト、lint、可能なら性能の回帰検出）。歴史的な測定値と現行値が分かれているか。

## 8. 互換性を約束する（19件）

既存ユーザーのコードや運用を壊さないことを明文化し、約束の範囲も示す。

- 効く理由: 安心して依存でき、エコシステムが育つ。
- 落とし穴: 範囲の広すぎる約束は守れない。守る境界を小さく明確にする。
- 取り入れ方: 公開APIの境界（接頭辞・ディレクトリ）を決め、そこだけ守ると約束する。
- 例: Go（ソースレベルに限定）、Rust（Edition）、TypeScript、Black、Neovim、curl（`curl_` 接頭辞）
- リポジトリで確認する観点: 公開境界（CLIのサブコマンドと引数、JSON出力キー、終了コード、設定ファイルのschema、public API）が宣言されているか。`schemaVersion` などの版があるか。契約テストで境界を固定しているか。名前と意味がずれた互換キーを放置していないか。

## 9. 意見のある既定値を選ぶ（19件）

設定を増やさず、最良と考える既定値や規約を提供する。

- 効く理由: 導入が速く、スタイル論争がなくなる。
- 落とし穴: 上書きの逃げ道がないと、大規模利用で困る。
- 取り入れ方: 新しいオプションの要望には、まず既定値の改善で解けないか検討する。
- 例: Go、Ruby on Rails、Prettier、Black、Biome、scikit-learn
- リポジトリで確認する観点: 既定値と、その根拠が書いてあるか。ハードコードされていて上書きの逃げ道がない値はないか。逆に、既定値を改善すべきところにオプションを増やしていないか。

## 10. 問題起点でスコープを守る（15件）

実在する問題だけを解き、受け入れ基準を明文化する。

- 効く理由: 保守対象が増えすぎず、プロジェクトが長生きする。
- 落とし穴: 基準が曖昧だと「あれは入れたのに」という不公平感を生む。
- 取り入れ方: PRテンプレートで「どんな実在の問題を解くか」を最初に書いてもらう。
- 例: esbuild、Homebrew、Redis、Godot（「問題が先」）、Elixir、Node.js
- リポジトリで確認する観点: 現行スコープ外のコードや文書（旧実装、実験）が同じ場所に混ざっていないか。Issue/PRテンプレートやロードマップに「解く問題」「受け入れ基準」の欄があるか。

## 11. ユーザー主権を守る（15件）

ローカル動作、データの持ち出し、ベンダーロックイン回避、プライバシーを重視する。

- 効く理由: 長期的な信頼と、熱心な支持者を得られる。
- 落とし穴: 利便性（クラウド連携など）とのバランスが必要。
- 取り入れ方: 「ユーザーのデータはどこにあり、どう持ち出せるか」を明記する。
- 例: Grafana、OpenTelemetry、Home Assistant、Deno、OpenTofu、Caddy
- リポジトリで確認する観点: 保存先の一覧、外部送信の境界、書き出し（export）と削除（purge）の手段、Telemetryの無効化方法があるか。

## 12. やらないことを宣言する（11件）

Non-goals、向いていない用途、追加しない機能を明記する。

- 効く理由: 断る判断が一貫し、同じ議論の繰り返しが減る。誤った期待を持つユーザーを早めに減らせる。
- 落とし穴: 理由のない拒否は反発を招く。代替手段とセットで書く。
- 取り入れ方: 要望を3回断ったら、その理由をNon-goalsに追記する。
- 例: TypeScript、Astro、esbuild、Prettier、Black、Neovim
- リポジトリで確認する観点: Non-goalsが1か所に一覧になっているか。それぞれに理由と代替手段があるか。

## 13. 貢献モデルを設計する（10件）

誰から・どんな貢献を・どう受けるかを意図して決める（受けない選択も含む）。

- 効く理由: メンテナの負担と品質をコントロールできる。
- 落とし穴: 方針を書かずに断ると、閉鎖的だと受け取られる。
- 取り入れ方: CONTRIBUTINGに「歓迎するもの」「受け入れにくいもの」を両方書く。
- 例: Neovim、Homebrew、Linux、SQLite（Open-Source, not Open-Contribution）、Transformers、Diffusers
- リポジトリで確認する観点: CONTRIBUTINGがあるか。歓迎するものと受け入れにくいものが両方書いてあるか。作者の関わり方（返信の速さ）の期待値を合わせているか。

## 14. 読み手と局所性を重視する（6件）

コードや振る舞いが、その場所を見るだけで理解できるようにする。

- 効く理由: 改造・貢献のハードルが下がる。
- 落とし穴: 重複が増えるので、同期の仕組みを用意する。
- 取り入れ方: 主要な処理は1ファイルで上から下まで読めるかを基準にする。
- 例: Zig、htmx、Transformers（1モデル1ファイル）、Diffusers、Python、ComfyUI
- リポジトリで確認する観点: 巨大なファイル（目安1000行超）が複数の責務を混ぜていないか。文書の同じ内容が複数か所に重複していないか（正本は1か所で、他はリンクにする）。

## 代表的な判断基準（Web確認済みの例）

| プロジェクト | 判断基準 |
| --- | --- |
| Go | 互換性は「ソースレベル」に限定。バイナリ互換や性能は約束しない |
| Rust | 破壊的変更はEditionでオプトイン。エコシステムを分断しない |
| TypeScript | Non-goalsの一覧（実行時型情報、独自ランタイム、E2Eビルドはしない） |
| Prettier / Biome | オプションは増やさない。既存オプションは歴史的経緯として扱う |
| Black | 設定を委ねる代わりに、速さ・決定性・議論からの自由を得る |
| esbuild | 性能を損なう機能は入れない。万能バンドラーは目指さない |
| Neovim | 迷ったら互換性。ただし利益が極めて大きければ使いやすさ |
| Godot | 問題が先。「問題を探している解決策」は退ける |
| SQLite | Open-Source, not Open-Contribution |
| Redis | 機能要望や質問への答え方に困ったからマニフェストを書いた |
| Transformers | DRYより「1モデル1ファイル」 |
| Linux | ユーザー空間を壊さない。壊れたらカーネル側のバグ |
